# 프로그램 매뉴얼: 설치부터 제출 함수 구현까지

이 문서는 프로그램 설치, 실행·결과 확인 방법, 그리고 학생이 작성할 함수의 입력·출력과
개발 순서를 설명합니다. 전체 소개와 문서 안내는 [README](../README.md), 경기 규칙은
[게임 규칙 매뉴얼](게임_규칙_및_운영_매뉴얼.md)을 참고하세요.

## 1. 설치

처음 한 번만 하면 됩니다. 아래 순서대로 명령어를 **복사해서 붙여 넣기**만 하면 됩니다.
이미 `my_baseball` conda 환경을 만들어 두었다면 4단계는 건너뛰고 5단계부터 진행하세요.

### 1단계: conda 설치하기

이 프로그램은 Python 패키지 관리자인 **conda**를 사용합니다. 둘 중 하나를 내려받아 설치하세요.
어느 쪽이든 이후 절차는 같습니다.

| 설치 파일 | 다운로드 링크 | 특징 |
|---|---|---|
| **Miniconda** (권장) | https://www.anaconda.com/download/success (페이지 아래쪽 *Miniconda Installers*) | 용량이 작고 필요한 것만 설치 |
| Anaconda Distribution | https://www.anaconda.com/download | 용량이 크지만 Jupyter 등 도구가 함께 설치됨 |

- 설치 중에 나오는 선택 항목은 **모두 기본값 그대로** 두고 *Next*를 누르면 됩니다.
- Windows에서 "Add Miniconda3 to my PATH" 체크박스는 체크하지 않아도 됩니다(2단계에서 Anaconda Prompt를 씁니다).
- 이미 Anaconda나 Miniconda가 설치되어 있다면 이 단계는 건너뜁니다.

### 2단계: 터미널 열기

- **Windows**: 시작 메뉴에서 `Anaconda Prompt`를 검색해 실행합니다. 일반 명령 프롬프트나
  PowerShell에서 `conda`를 찾을 수 없다는 오류가 나면 이 창을 사용하세요.
- **macOS / Linux**: 터미널(Terminal)을 엽니다. 설치 직후라면 터미널을 한 번 닫았다가 다시 엽니다.

설치가 잘 되었는지 다음 명령으로 확인합니다. 버전 번호가 출력되면 정상입니다.

```shell
conda --version
```

### 3단계: 프로젝트 내려받고 폴더로 이동하기

릴리즈 페이지 https://github.com/Kahkim/my_baseball/releases 를 열고, 맨 위에 있는 **최신 버전**의
**Source code (zip)**을 눌러 내려받습니다. 압축을 풀면 `my_baseball-1.0`처럼 버전이 붙은 폴더가 생깁니다.

터미널에서 그 폴더로 이동합니다. 예를 들어 바탕화면에 풀었다면 다음과 같습니다(폴더 이름은 실제 이름에 맞춰 바꾸세요).

```shell
cd Desktop\my_baseball-1.0
```

`README.md`와 `requirements.txt`가 보이는 폴더가 **프로젝트 최상위 폴더**입니다.
이 문서의 명령은 모두 이 폴더에서 실행합니다.

### 4단계: conda 환경 만들기

```shell
conda create -n my_baseball python=3.12 pip -y
```

`my_baseball`이라는 이름의 독립된 Python 3.12 환경이 만들어집니다. 1~2분 정도 걸립니다.

### 5단계: 환경 활성화하기

```shell
conda activate my_baseball
```

프롬프트 앞에 `(my_baseball)`이 붙으면 성공입니다. **터미널을 새로 열 때마다 이 명령을 다시 실행**해야 합니다.

### 6단계: 필요한 패키지 설치하기

```shell
python -m pip install -r requirements.txt
```

### 7단계: 설치 확인하기

```shell
python -m kbo_sim.cli --help
```

옵션 설명이 길게 출력되면 설치가 끝난 것입니다. `No module named kbo_sim` 오류가 나면
3단계의 프로젝트 최상위 폴더에 있는지 확인하세요.

> **PowerShell에서도 conda를 쓰고 싶다면** Anaconda Prompt에서 `conda init powershell`을
> 한 번 실행하고 PowerShell을 새로 엽니다. 이후에는 PowerShell에서도 `conda activate`가 동작합니다.

## 2. 라이브 서버 실행하기

브라우저에서 경기를 한 이닝씩 진행하며 지켜보는 방식입니다. 동봉된 **학생용 템플릿**을 그대로
올려서 바로 경기를 볼 수 있으므로, 내 알고리즘을 만들기 전에 프로그램이 어떻게 돌아가는지 먼저 확인해 보세요.

### 1단계: 환경 활성화하기

터미널을 새로 열었다면 프로젝트 최상위 폴더로 이동한 뒤 환경을 활성화합니다.

```shell
conda activate my_baseball
```

### 2단계: 서버 실행하기

```shell
python -m kbo_sim.server
```

터미널에 `[라이브 서버] http://127.0.0.1:8000 에서 실행 중` 이라고 표시되고 브라우저가 자동으로 열립니다.
열리지 않으면 브라우저 주소창에 `http://127.0.0.1:8000`을 직접 입력하세요.
서버가 켜져 있는 동안 이 터미널 창은 닫지 마세요.

### 3단계: 이름·구단 입력하고 템플릿 파일 올리기

브라우저 화면에서 두 학생 A/B의 정보를 채웁니다.

1. 학생 A/B의 **이름**을 입력합니다.
2. 학생 A/B의 **구단**을 서로 다르게 고릅니다(예: A는 `삼성`, B는 `KT`).
3. **알고리즘 파일**을 올립니다. 처음에는 동봉된 예제를 그대로 사용하세요.

| 학생 | 올릴 파일 | 설명 |
|---|---|---|
| A | [examples/student_algorithm_template.py](../examples/student_algorithm_template.py) | 학생용 템플릿. 나중에 여러분이 수정할 출발점 |
| B | [examples/strategy_naive_best.py](../examples/strategy_naive_best.py) | 체력을 무시하는 대조군 예제 |

두 쪽 모두 템플릿을 올려도 됩니다. 내 알고리즘을 만든 뒤에는 그 파일을 대신 올리면 됩니다.

### 4단계: 검사 결과 확인하기

파일을 올리면 자동으로 검사합니다. 검사는 **10명 선발 1회 → 선발 9명 타순 결정 1회** 순서로 한 번씩 실행합니다.

- **오류**가 있으면 경기를 시작할 수 없습니다. 파일을 고쳐서 다시 올리세요.
- **경고**는 내용을 읽어 보고 필요하면 수정합니다. 경고만으로 시작이 막히지는 않습니다.

동봉된 예제는 오류 없이 통과합니다.

### 5단계: 경기 진행하기

1. **[경기 준비 완료 → 3연전 시작]**을 누릅니다.
2. **[다음 라인업 선발] → [다음 공격 진행(초)] → [다음 공격 진행(말)]**을 반복해서 누릅니다.
   라인업 버튼은 학생 알고리즘을 실행하고, 공격 진행 버튼은 확정된 명단으로 경기 엔진을 실행합니다.
3. 버튼을 일일이 누르기 번거로우면 **자동진행**을 켭니다. 자동진행을 켜도 경기가 끝나면 멈춥니다.
4. 한 경기가 끝나면 점수를 확인하고 **[다음 경기 시작]**을 눌러 3경기까지 진행합니다.

화면에는 이닝별 점수(R)·안타(H)·실책(E), 양 팀 명단·체력·계산시간·투구 중계가 표시됩니다.
경기가 끝날 때마다 `output/game1.json`~`game3.json`이 저장됩니다(4절 참고).

### 6단계: 서버 종료하기

터미널 창에서 `Ctrl+C`를 누르면 서버가 종료됩니다.

### 알아 두면 좋은 것

- **파일을 수정했다면 다시 올리기**: 업로드는 매번 별도 폴더에 저장하므로 원본을 고쳐도 화면에는 반영되지 않습니다.
  수정한 파일은 **다시 업로드**해야 적용됩니다.
- **새로고침**하면 실행 중인 서버의 현재 경기 상태를 복구합니다. 서버를 껐다 켜면 진행 중 상태는 복구되지 않습니다.
- **포트가 이미 사용 중**이라는 오류가 나면 `--port 8001`처럼 다른 포트를 지정합니다.

## 3. 여러 번 반복해 종합 결과 보기

야구는 원래 분산이 큰 스포츠입니다. 3경기(3연전 1회)만 보고는 내 알고리즘이 실제로 더 나은지,
우연히 이겼는지 구분하기 어렵습니다. 그래서 내 알고리즘을 평가할 때는 화면 조작 없이
**같은 대진을 3연전 단위로 N번 반복**하고, 시리즈 단위·경기 단위 종합 성적을 함께 보는 방식을 사용합니다.

### 1단계: 환경 활성화하기

```shell
conda activate my_baseball
```

### 2단계: 내 알고리즘 파일 만들기

[학생용 템플릿](../examples/student_algorithm_template.py)을 `my_algo.py`라는 이름으로 프로젝트 최상위 폴더에 복사합니다.

```shell
copy examples\student_algorithm_template.py my_algo.py
```

macOS / Linux에서는 다음 명령을 사용합니다.

```shell
cp examples/student_algorithm_template.py my_algo.py
```

이제 `my_algo.py`의 `decide_lineup` 함수를 수정해 나가면 됩니다(5절 이후 참고).
처음에는 템플릿 그대로 실행해 보고, 결과가 나오는 것을 확인한 뒤 수정을 시작하세요.

### 3단계: 반복 실행하기

내 알고리즘(A)과 대조군 예제(B)를 3연전 20회, 총 60경기 맞붙입니다.

```shell
python -m kbo_sim.cli --a-name 나 --a-team 삼성 --a-algo my_algo.py --b-name 상대 --b-team KT --b-algo examples/strategy_naive_best.py --seed 12345 --repeat 20 --out output/my_test_repeat
```

먼저 두 파일을 검사하고, 통과하면 반복이 시작됩니다. 반복이 하나 끝날 때마다 다음처럼 한 줄씩 출력됩니다.

```text
[반복 1/20] (시드 1234567) 3연전 승점 나 2.0 : 1.0 상대  승자: A  -> output/my_test_repeat/rep01/
```

알고리즘 실행시간과 PC 성능에 따라 완료까지 시간이 걸립니다. 처음에는 `--repeat 5` 정도로
짧게 돌려 보고, 잘 동작하면 횟수를 늘리세요. 호출당 제한시간(기본 10초)을 넘기면 그 이닝은
기본 명단으로 대체되므로(11절 참고), 작은 후보 수와 적은 반복으로 시작해 실행시간을 확인하면서 키우는 것이 안전합니다.

### 4단계: 종합 결과 읽기

반복이 모두 끝나면 콘솔에 종합 결과가 출력됩니다.

```text
======================================================================
종합 결과 (20회 반복 = 60경기)
======================================================================
[3연전 단위, 총 20회]
  나: 13승 1무 6패 (승률 67.5%)
  상대: 6승 1무 13패 (승률 32.5%)

[경기 단위, 총 60경기]
  나: 37승 0무 23패 (승률 61.7%, 95% 신뢰구간 49.0~73.0%)
  상대: 23승 0무 37패 (승률 38.3%, 95% 신뢰구간 27.0~51.0%)

경기당 평균 득실차 (나 기준): +0.85
-> 경기 단위 신뢰구간이 50%를 포함합니다. 이 표본으로는 우열을 가릴 수 없습니다 (--repeat를 늘려보세요).
```

| 항목 | 보는 법 |
|---|---|
| 3연전 단위 승/무/패 | 시리즈를 몇 번 이겼는지. 실제 대회 방식과 같은 단위 |
| 경기 단위 승률 + 95% 신뢰구간 | **신뢰구간 하한이 50%를 넘으면** 우연이 아니라 실제로 더 잘하는 것. 구간이 50%를 포함하면 이 표본으로는 우열을 가릴 수 없으므로 `--repeat`를 늘려 다시 확인 |
| 경기당 평균 득실차 | 이길 때 얼마나 크게 이기고 질 때 얼마나 작게 지는지. 승률이 비슷할 때 보조 지표 |

승패뿐 아니라 실행 중 콘솔에 이닝별로 출력되는 **계산시간**(`[3회] 삼성 출전 10명·타순 결정 (1.23초)`)과
**알고리즘 실패 메시지**(`[삼성] 알고리즘 timeout (...) -> 직전 이닝 명단 재사용`)도 함께 보세요.
시간 초과로 명단이 대체되는 이닝이 많다면 승률보다 실행시간부터 줄여야 합니다.
후반 이닝의 체력 변화는 저장된 경기 파일을 리플레이 뷰어로 열어 확인할 수 있습니다(5단계 참고).

### 5단계: 저장된 결과 확인하기

`--out`으로 지정한 폴더에 다음 파일이 남습니다.

| 경로 | 내용 |
|---|---|
| `output/my_test_repeat/repeat_summary.json` | 종합 결과. 반복별 시드·점수·승자, 시리즈/경기 단위 기록, 신뢰구간, 평균 득실차 |
| `output/my_test_repeat/rep01/game1.json` … | 반복 번호별 하위 폴더에 저장된 경기 파일. [리플레이 뷰어](../viewer/broadcast_viewer.html)로 열어 볼 수 있음 |

반복마다 3연전 대진·시드는 서로 다르게 뽑힙니다. 같은 `--seed`를 주면 이 시드열 자체가 재현되므로
알고리즘을 수정한 전후를 **같은 조건에서** 비교할 수 있습니다.
`--out` 폴더를 다시 사용하면 같은 이름의 파일을 덮어쓰므로, 실험마다 `--out output/test_02`처럼 폴더를 나누세요.

### 6단계: 조건을 바꿔 다시 평가하기

한 구단·한 상대로만 이긴 결과는 그 구단에 맞춘 우연일 수 있습니다. 다음처럼 조건을 바꿔 여러 번 평가하세요.

- **구단 교체**: `--a-team LG --b-team 두산`처럼 다른 구단 조합으로 실행합니다.
  3연전 안에서도 경기마다 구단이 바뀌므로 어느 구단을 맡아도 동작해야 합니다.
- **상대 교체**: `--b-algo examples/example_tabu_lineup.py`처럼 Tabu Search 예제와 맞붙여 봅니다.
- **시드 교체**: `--seed` 값을 바꾸거나 생략(무작위)해서 시드열이 달라져도 결과가 유지되는지 확인합니다.

### 실행 옵션

| 옵션 | 서버 | CLI | 의미 |
|---|---|---|---|
| `--a-name`, `--b-name` | 선택 | 필수 | 학생 이름 |
| `--a-team`, `--b-team` | 선택 | 필수 | 구단 이름 |
| `--a-algo`, `--b-algo` | 선택 | 필수 | 제출 `.py` 경로 |
| `--seed` | 선택 | 선택 | 재현용 시드. 생략하면 무작위 |
| `--timeout` | 기본 10초 | 기본 10초 | 알고리즘 호출당 제한시간 |
| `--out` | 기본 `output` | 기본 `output` | 경기 결과 저장 폴더 |
| `--repeat` | 없음 | 기본 1 | 3연전을 이 횟수만큼 반복해 종합 결과를 냅니다. 생략하거나 1이면 3연전 1회만 실행하고 `match_summary.json`을 남깁니다 |
| `--data-dir` | 선택 | 선택 | CSV 4개가 있는 데이터 폴더 |
| `--port` | 기본 8000 | 없음 | 서버 포트 |

라이브 API의 `points`도 ID를 키로 사용합니다. 기존에 저장된 JSON은 자동 변환하지 않습니다.

## 5. 제출할 파일과 함수

[학생용 템플릿](../examples/student_algorithm_template.py)을 복사해 `학번_이름.py`처럼 저장합니다.
Python 파일 하나 안에 다음 함수를 **파일 최상위**에 정의하세요. 보조 함수는 같은 파일에 추가할 수 있습니다.
파일 인코딩은 UTF-8로 저장합니다.

```python
def decide_lineup(my_team, opponent_team, matchups, context, rng):
    # 선수 선택과 타순 탐색을 구현합니다.
    return {"defense": [], "offense": []}
```

위 코드는 함수 모양만 보여 줍니다. 빈 리스트로 제출하면 검증에 실패합니다.
실제로 실행 가능한 최소 예제는 9절에 있습니다.

**함수 이름과 다섯 인자의 이름·순서를 유지하세요.** 엔진이 키워드 인자로 호출하고,
사전 검사도 이 시그니처를 확인합니다. 클래스 안의 메서드나 다른 함수 안의 내부 함수로 만들면 안 됩니다.
한 번의 호출로 `{"defense": [10명], "offense": [9명]}` dict를 반환해 공격 타순과 수비 배치를 함께 정합니다.

학생이 반환할 것은 선수의 이름이나 행 번호가 아니라 **`pCode` 정수 리스트**입니다.
`pCode`는 선수 식별자이고, 참가자 A/B는 3연전 점수 집계용 식별자입니다. 서로 다른 개념입니다.

## 6. 언제 호출되고 무엇을 알 수 있나요?

```text
이닝 시작: 홈팀 decide_lineup 1회 → 원정팀 decide_lineup 1회
경기 진행: 초 공격(원정) → 말 공격(홈)
```

전체 호출은 이닝당 2회(팀당 1회)이며, **내 함수는 이닝마다 한 번** 호출되어 그 이닝의
공격 타순과 수비 배치를 한꺼번에 반환합니다. 초·말 공수교대 때 추가로 호출하지 않습니다.
따라서 홈팀도 초 공격 결과가 나오기 전에 이번 이닝 명단을 모두 정합니다. 양 팀 명단을 이닝
시작에 동시에 정하므로 **이번 이닝에 상대할 투수/포수는 아직 알 수 없습니다.**
누가 등판할지는 모르지만, `opponent_team`에는 상대 투수 **전원**의 기록·체력이, `matchups`에는
그 투수 전원과 우리 타자들의 맞대결이 들어옵니다. "모른다"는 것은 정보가 없다는 뜻이 아니라,
후보가 여러 명이라는 뜻입니다.

| 인자 | 타입 | 용도 |
|---|---|---|
| `my_team` | `pandas.DataFrame` | 우리 구단 전체 선수(타자+투수)의 기록과 체력 |
| `opponent_team` | `pandas.DataFrame` | 상대 구단의 전체 타자·투수 기록과 체력 |
| `matchups` | `pandas.DataFrame` | 양 팀 **투수 전원 × 상대 타자 전원**의 맞대결 기록 (6.2절) |
| `context` | `dict` | 이닝·점수·타순 시작 위치·이전 명단 등 |
| `rng` | `random.Random` | 이번 호출 전용 난수 생성기 |

### 6.1 `my_team`과 `opponent_team`

한 행이 선수 한 명입니다. 먼저 `role`로 타자와 투수를 구분하세요.
두 DataFrame의 컬럼 구성은 같고, 상대 선수의 체력도 볼 수 있습니다.
`my_team`에는 우리 구단 전체 선수가 들어옵니다. 이 중에서 수비 10명을 고르고, 투수를 제외한
9명의 타순을 정합니다. 행 순서를 수비 자리로 해석하지 마세요 — 자리 배정은 여러분이 반환하는
`defense` 리스트의 순서로 결정됩니다.

```python
batters = my_team[my_team["role"] == "타자"]
pitchers = my_team[my_team["role"] == "투수"]
```

| 구분 | 주요 컬럼 | 읽는 방법 |
|---|---|---|
| 식별 | `pCode` | 반환값에 넣을 선수 번호 |
| 표시 | `name`, `shortName`, `displayId`, `team`, `backNo` | 이름·구단·등번호. 선수 선택의 고유 키는 `pCode` |
| 포지션 | `position`, `role`, `throwBat` | `position`: 내야수/외야수/포수/투수, `role`: 타자/투수 |
| 체력 | `health_pct` | 높을수록 덜 지친 상태. 확률 자체가 아님 |
| 타자 소모 | `swing_count`, `swing_target` | 타격·수비의 누적 환산 스윙 수와 이번 경기 기준치 |
| 투수 소모 | `pitch_count`, `pitch_target` | 누적 투구 수와 이번 경기 기준치 |
| 타격 지표 | `AVG`, `OBP`, `SLG`, `OPS`, `PA`, `AB` | 타율·출루율·장타율·OPS와 표본 크기 |
| 투구 지표 | `ERA`, `WHIP`, `TBF`, `NP`, `G` | 방어율·이닝당 출루 허용 지표·상대 타자 수·투구 수·등판 수 |
| 계산된 값 | `PA_eff`, `TBF_eff`, `NP_per_G`, `target_pitch_base`, `IP_f` | 엔진이 계산한 유효 표본 수·평균 투구 수·목표치 기준·숫자형 이닝 |

`health_pct`는 경기 중 낮아지고, `swing_count`와 `pitch_count`는 누적됩니다.
벤치에 있어도 회복하지 않지만 새 경기는 초기화된 상태로 시작합니다.
타자에게 투수 전용 값, 투수에게 타자 전용 값은 결측일 수 있으므로 역할을 나눈 뒤 사용하세요.

**같은 컬럼도 역할에 따라 뜻이 다릅니다.** 예를 들어 `H`, `HR`, `BB`, `SO`는 타자 행에서는
자신의 안타·홈런·볼넷·삼진이고, 투수 행에서는 허용 안타·허용 홈런·허용 볼넷·탈삼진입니다.
`G`도 타자 출전 경기 수와 투수 등판 수를 구분해서 읽습니다.

현재 데이터에는 다음 기록도 포함됩니다. 첫 구현에서 전부 사용할 필요는 없습니다.

| 역할 | 추가 기록 컬럼 |
|---|---|
| 타자 | `R`, `H`, `2B`, `3B`, `HR`, `TB`, `RBI`, `SAC`, `SF`, `BB`, `IBB`, `HBP`, `SO`, `GDP`, `MultiHit`, `RISP_AVG`, `PH_AVG` |
| 투수 | `W`, `L`, `SV`, `HLD`, `WPCT`, `IP`, `ER`, `CG`, `SHO`, `QS`, `BSV`, `OAVG`, `WP`, `BK`와 피안타·사사구·탈삼진 관련 컬럼 |

`PA_eff`, `TBF_eff` 등은 원본 기록 자체와 구분해야 합니다.
`AVG`, `OPS`, `ERA`는 개인 기록 값이며, 엔진 내부에서 확률을 만들 때 쓰는 표본 축소가 적용된 지표는 아닙니다.
표본이 적은 선수의 극단적인 기록을 그대로 높게 평가하지 않도록 표본 크기도 함께 보세요.
내부 확률 딕셔너리 `event_rate`와 `event_counts`는 학생용 DataFrame에 제공하지 않습니다.

### 6.2 `matchups`

| 포함되는 조합 |
|---|
| 우리 팀 **전체 투수** × 상대 팀 **전체 타자** (수비·투수 선택용) |
| 상대 팀 **전체 투수** × 우리 팀 **전체 타자** (타순 결정용) |

두 방향이 대칭입니다. `opponent_team`에 상대 투수 전원의 시즌기록·체력이 보이는 것과 같이,
`matchups`도 상대 불펜을 포함한 **투수 전원**을 조회 대상으로 삼습니다. 1회에도 마찬가지입니다 —
상대의 직전 이닝 투수가 정해지기 전이어도 표는 채워져 있습니다. 다만 **이번 이닝에 실제로 누가
마운드에 오를지는 여전히 알 수 없으므로**, 등판 가능성으로 가중한 기댓값으로 다루세요.

위 조합 중 동봉된 맞대결 데이터에 실제 기록이 있는 행만 전달됩니다. 여기서 "전원"은 **조회
대상**이지 실제 행이 있는 인원이 아닙니다 — 통산 맞대결이 한 번도 없는 조합은 행 자체가 없어서,
실제로 행이 붙는 상대 투수는 로스터의 **평균 76%(대진에 따라 59~90%)**입니다. 한 타자에 붙는
상대 투수는 중앙값 10명입니다. 즉 등판 후보 중 일부는 맞대결 정보가 아예 없으니 개인 시즌기록
으로만 평가해야 하고, **특정 투수–타자 쌍의 행은 여전히 없을 수 있습니다.** 데이터를 교체하면
표가 통째로 빌 수도 있으니 빈 표에서도 동작하도록 작성하세요.
기록이 없는 조합을 반드시 패배하거나 확률이 0인 조합으로 취급하지 마세요.

컬럼은 `pitcherPCode`, `hitterPCode`, `AVG`, `PA`, `AB`, `H`, `2B`, `3B`, `HR`,
`RBI`, `BB`, `HBP`, `SO`, `SLG`, `OBP`, `OPS`입니다.
선수 쌍을 찾을 때는 이름 대신 두 pCode를 사용합니다.

```python
matchup_lookup = {
    (int(row["pitcherPCode"]), int(row["hitterPCode"])): row
    for _, row in matchups.iterrows()
}
```

상대 투수가 여러 명이므로 투수별로 묶어 두면 "이 투수가 올라오면 우리 타선은 어떤가"를
후보마다 빠르게 비교할 수 있습니다.

> **주의 — 반드시 방향을 걸러야 합니다.** 이 표에는 `우리 투수 × 상대 타자`(수비용)와
> `상대 투수 × 우리 타자`(공격용)가 **함께** 들어 있습니다. `pitcherPCode`로만 묶으면
> 우리 팀 투수까지 "등판 후보"로 잡혀서, 실측 기준 후보의 절반가량이 우리 타자에 대해
> 아무 기록도 없는 유령 후보가 됩니다. 그대로 기댓값을 내면 조용히 희석됩니다.

```python
from collections import defaultdict

my_batters = set(my_team.loc[my_team["role"] == "타자", "pCode"])

by_pitcher = defaultdict(dict)          # 상대 투수 pCode -> {우리 타자 pCode: 기록}
for row in matchups.to_dict("records"):  # iterrows()보다 빠릅니다
    h = int(row["hitterPCode"])
    if h in my_batters:                  # 공격용(상대 투수 × 우리 타자)만 남긴다
        by_pitcher[int(row["pitcherPCode"])][h] = row
```

### 6.3 `context`

| 키 | 값 | 의미 |
|---|---|---|
| `inning` | `int` | 현재 이닝. 기본 설정에서는 1~9 |
| `half` | `"top"` 또는 `"bottom"` | 우리 팀이 공격하는 하프 (원정=top, 홈=bottom) |
| `my_score`, `opponent_score` | `int` | 이닝 시작 시점의 점수 |
| `outs` | `0` | 명단 결정 때는 항상 0 |
| `batting_order_start_index` | `0`~`8` | 반환할 `offense` 9명 중 실제 선두타자가 서는 위치 |
| `my_prev_offense` / `my_prev_defense` | 리스트 또는 `None` | 우리 팀 직전 이닝 타순 / 수비 배치 |
| `opp_prev_offense` / `opp_prev_defense` | 리스트 또는 `None` | 상대 팀 직전 이닝 타순 / 수비 배치 |
| `opp_pitcher_pcode` | 정수 또는 `None` | 상대의 **직전 이닝** 투수 (`opp_prev_defense[9]`). 1회엔 `None` |
| `opp_catcher_pcode` | 정수 또는 `None` | 상대의 **직전 이닝** 포수 (`opp_prev_defense[7]`). 1회엔 `None` |
| `time_budget_sec` | 숫자 | 호출당 제한시간. 기본 10초 |

양 팀이 이닝 시작에 동시에 명단을 정하므로 `opp_pitcher_pcode` 등은 **이번 이닝이 아니라
직전 이닝** 기준입니다(첫 이닝은 `None`). 실패한 호출이 기본 명단으로 대체됐다면 그 대체
명단이 최근 확정 명단으로 남습니다.

반환한 타순은 `batting_order_start_index`부터 사용합니다.
예를 들어 값이 `4`라면 리스트의 다섯 번째 선수가 선두입니다.
리스트를 회전시켜 돌려주면 엔진이 다시 그 리스트의 인덱스 4부터 시작하므로, 원하는 선수를 그 자리에 배치하세요.

### 6.4 `rng`

난수가 필요하면 `rng.random()`, `rng.sample()`, `rng.shuffle()` 등을 사용합니다.
같은 초기 시드와 같은 호출 순서에서는 재현되지만, **호출마다 새 난수열이 전달**됩니다.

전역 `random`, `random.seed()`, `numpy.random` 대신 인자로 받은 `rng`를 쓰세요.
학생용 RNG와 엔진용 RNG는 분리되어 있으므로 학생의 난수 호출 횟수가 엔진 난수열을 직접 소비하지 않습니다.
물론 난수로 선택한 **라인업이 달라지면 경기 결과도 달라질 수 있습니다.**

## 7. 반환값 규칙

`{"defense": [10명], "offense": [9명]}` 형태의 dict를 반환합니다.

### `offense`: 타자 9명

타순 1번부터 9번 순서로 pCode를 반환합니다. **`defense`의 앞 9명(투수 제외)과 정확히 같은
9명**이어야 하며 순서만 바꿀 수 있습니다. 벤치 선수를 넣으면 무효입니다.
실제 선두타자는 앞서 설명한 `batting_order_start_index`로 정해집니다.

### `defense`: 10자리의 고정 순서

| 리스트 인덱스 | 자리 | 허용 선수 |
|---|---|---|
| `0`~`3` | 내야수 4자리 | 우리 팀 타자 |
| `4`~`6` | 외야수 3자리 | 우리 팀 타자 |
| `7` | 포수 | 우리 팀 타자 |
| `8` | DH | 우리 팀 타자. 수비 소모·포지션 실책 페널티 없음 |
| `9` | 투수 | 우리 팀의 실제 투수만 |

공격·수비 모두 길이를 지키고, 중복이나 다른 팀 선수 없이 **정수 리스트**를 반환하세요.
**공격 명단은 수비 앞 9명과 같은 선수로 구성해야 합니다(DH 포함).**
이닝 시작에 10명을 확정한 뒤에는 투수를 포함해 공수교대 때 교체하지 않습니다. 다음 이닝 시작에는 다시 선발할 수 있습니다.

내야·외야·포수에 포지션이 다른 타자를 배치하는 것은 허용되지만 해당 선수가 수비에 관여할 때
실책 확률에 1.5배가 적용됩니다. DH는 예외입니다.
현재 포수는 일반 타구 처리 수비수로 선택되지 않으며, 도루 저지 능력도 별도 반영하지 않습니다.

## 8. 개발 순서

1. 먼저 어느 구단을 맡아도 유효한 수비 10명을 선발하고, 그중 투수 제외 9명의 타순을 함께 반환하게 만듭니다.
2. 체력과 기록으로 선수를 평가하는 함수를 작성합니다.
3. 후보를 어떻게 표현할지 정합니다. 예: 수비는 선수·포지션 배정, 공격은 그 9명의 타순 순열.
4. 탐색 중에도 중복 선수·투수 자리 등 명단 규칙을 지키도록 합니다.
5. 실행시간을 측정하며 탐색 반복 수를 조정합니다.
6. 같은 조건으로 baseline과 비교하고, 여러 시드·팀으로 다시 평가합니다(3절의 `--repeat` 참고).

이닝마다 맡을 구단이 바뀌는 것은 아니지만 **3연전의 경기 사이에는 구단이 바뀝니다.**
선수 번호를 고정하지 말고 매 호출의 `my_team`에서 후보를 만드세요.

## 9. 최소 동작 예제

아래는 명단 규칙과 함수 연결을 확인하기 위한 **탐색 없는 예제 전체**입니다.
`my_algo.py`에 저장하면 동봉된 10개 구단에서 사용할 수 있습니다.
승률을 높이는 전략은 직접 추가해야 합니다.

```python
def decide_lineup(my_team, opponent_team, matchups, context, rng):
    batters = my_team[my_team["role"] == "타자"]
    pitchers = my_team[my_team["role"] == "투수"]
    codes = [int(p) for p in batters["pCode"].tolist()]

    def first_at(position, count):
        selected = batters[batters["position"] == position]["pCode"].tolist()
        return [int(p) for p in selected[:count]]

    infield = first_at("내야수", 4)
    outfield = first_at("외야수", 3)
    catcher = first_at("포수", 1)
    used = set(infield + outfield + catcher)
    dh = next(p for p in codes if p not in used)
    pitcher = int(pitchers["pCode"].iloc[0])
    defense = infield + outfield + catcher + [dh, pitcher]

    return {"defense": defense, "offense": defense[:9]}
```

체력과 표본 크기 보정까지 포함한 출발점은
[학생용 템플릿](../examples/student_algorithm_template.py)을 보세요. 템플릿의 점수식은 참고용 휴리스틱이며
경기 엔진의 확률 계산식 자체가 아닙니다. 문서에 템플릿 전체를 중복해서 싣지 않으므로 최신 코드는 링크한 파일을 사용하세요.

### 숫자 0과 결측값을 구분하세요

`value or default`는 체력 0, ERA 0.00도 기본값으로 바꿉니다. 다음처럼 결측 여부를 직접 확인합니다.

```python
import pandas as pd


def number_or_default(value, default):
    return default if pd.isna(value) else float(value)
```

적합도 함수에서 여러 번 참조할 데이터는 탐색 전에 dict나 배열로 정리하세요.
매 후보 평가마다 전체 DataFrame을 다시 필터링하면 반복 수에 비례해 비용이 커집니다.

## 10. TS 구현 전략 예시

Tabu Search(TS)를 직접 구현할 때는 **해를 탐색하는 부분과 해의 점수를 계산하는 목적함수
`fit()`을 분리**하는 것이 좋습니다. 같은 목적함수를 GA에도 연결하면 탐색 방식의 차이를 비교할 수 있습니다.
아래 내용은 학생이 개선할 수 있는 설계 예시이며, 경기 엔진의 정확한 기대득점 계산식은 아닙니다.

### 10.1 타순을 바꾸면 목적함수 값도 달라져야 합니다

다음처럼 선수별 점수만 더하면 같은 9명의 순서를 바꾸어도 점수가 같습니다.

```python
score = sum(batter_score(p) for p in offense)
```

이 식은 출전 선수 선택에는 사용할 수 있지만, 타순 교환을 평가하지 못합니다.
[Tabu 예제](../examples/example_tabu_lineup.py)는 타순별 OBP·SLG 가중치로 이 문제를 보완합니다.
다만 선수와 자리의 점수가 서로 독립적이면 배정 문제이므로, 선수 조합의 상호작용을 찾는 탐색의
장점은 제한적입니다. 앞 타자의 출루와 뒤 타자의 장타처럼 **인접 타자의 연결 효과**를 추가해 보세요.

### 10.2 개별 기여와 연결 효과, 실점 비용을 함께 봅니다

출발점으로 다음과 같은 최대화 목적함수를 사용할 수 있습니다.

```text
F(x) = Σ w[t] × A(b[t])
     + λ × Σ v[t] × OBP_adj(b[t]) × SLG_adj(b[t+1])
     − α × P(p) − β × D(x) − γ × C(x)
```

첫 번째 합은 `t=0..8`, 연결 효과의 합은 `t=0..7`로 계산하는 간단한 근사입니다.
한 바퀴 뒤 마지막 타자와 첫 타자의 연결까지 반영하려면 추가 타석에 도달할 가능성도 고려해 확장합니다.

| 항목 | 의미와 설계 방향 |
|---|---|
| `x` | 수비 10명 배정과 그중 타자 9명의 공격 순서를 포함한 해 |
| `b[t]` | 이번 이닝에 실제로 타석에 서는 순서의 타자 |
| `A`, `OBP_adj`, `SLG_adj` | 표본 크기와 체력을 보정한 타격 지표 |
| `w[t]`, `v[t]` | 실제 타격 순서별 기여와 연결 효과의 가중치 |
| `P(p)` | 투수 기록과 이번 이닝을 버틸 체력·투구 여력을 반영한 실점 위험 |
| `D(x)` | 수비 기회, 포지션 불일치와 체력을 반영한 실책 비용 |
| `C(x)` | 지금 출전시켜 소모하는 체력 때문에 이후 이닝에 잃는 가치의 근사 |
| `λ`, `α`, `β`, `γ` | 각 항목의 영향력을 조절하는 가중치 |

`OBP_adj × SLG_adj`는 출루 뒤 장타의 연결을 표현하는 교육용 가설입니다. 실제 득점과의 관계는
경기 실험으로 확인해야 합니다. 서로 단위가 다른 항목은 크기를 맞춘 뒤 가중치를 조절하고,
초급 구현에서는 향후 체력 비용 `C(x)`를 생략해도 됩니다. 현재 체력에 따른 능력 저하와
향후 체력 소모 비용을 구분하여 같은 영향을 중복 감점하지 않도록 합니다.

표본 보정은 템플릿처럼 `n / (n + k)`를 사용하여 표본이 적을수록 리그 평균 쪽으로 당기는 방식으로
시작할 수 있습니다. 타자는 `PA_eff`, 투수는 `TBF_eff` 등을 참고하고, 맞대결 기록도 표본이 작으면
개인 기록 기반 추정 쪽으로 보정합니다. 상대 직전 이닝 투수를 그대로 쓰는 것은 "이번에도 같은
투수가 등판한다"고 가정한 평가입니다. `matchups`에는 상대 투수 전원의 맞대결이 들어오므로,
직전 이닝 투수 한 명에 걸지 말고 **등판 가능성으로 가중한 기댓값**(예: 직전 이닝 투수에 큰
가중치, 나머지 불펜에 남은 가중치를 체력·투구 여력으로 배분)으로 평가하는 설계도 가능합니다.
특정 투수–타자 쌍의 맞대결 기록이 없는 경우의 기본값은 여전히 준비해야 합니다.

실제 타격 순서는 다음과 같이 구합니다. 이 리스트는 평가용이며, 반환할 `offense`는 엔진이
`start`부터 읽는다는 점을 유지하세요.

```python
start = context.get("batting_order_start_index", 0)
actual_order = offense[start:] + offense[:start]
```

### 10.3 평가 함수와 TS 탐색기를 분리합니다

아래는 함수 역할을 보여 주는 구조 예시입니다. `prepare`, `is_valid`, `evaluate`는 직접 구현할
보조 함수이며, 이 코드만으로 제출할 수는 없습니다.

```python
prepared = prepare(my_team, opponent_team, matchups, context)

def fit(solution):
    if not is_valid(solution, prepared):
        return float("-inf")
    return evaluate(solution, prepared)  # 클수록 좋은 해
```

`prepare()`에서 선수 보정값과 맞대결 조회표를 한 번 계산하고, `fit()`은 같은 입력과 같은 해에
항상 같은 점수를 반환하도록 만듭니다. 후보마다 DataFrame을 필터링하거나 전체 경기를 여러 번
시뮬레이션하면 기본 10초 제한을 넘기기 쉽습니다. 같은 해의 평가값은 이번 호출 안에서 캐싱할 수
있지만, 다음 이닝에는 체력과 상황이 바뀌므로 그대로 재사용할 수 없습니다.

TS는 다음 순서로 구성할 수 있습니다.

1. 기록과 체력으로 유효한 초기 명단과 타순을 만들고, 현재해와 최고해를 저장합니다.
2. 타순 두 자리 교환, 수비 자리 교환, 벤치 타자 교체, 투수 교체로 이웃해를 만듭니다.
   벤치 타자를 넣으면 수비와 공격 명단을 함께 갱신하여 같은 9명을 유지합니다.
3. 각 이웃해를 `fit()`으로 평가하고, 허용된 후보 중 가장 좋은 해로 이동합니다.
   현재해보다 나빠지는 이동도 허용하되 최고해는 별도로 보존합니다.
4. 방금 이동을 되돌리는 속성을 일정 반복 동안 tabu로 등록합니다. 예를 들어 교체로 빠진 선수가
   원래 자리로 돌아오는 이동을 금지합니다. 전체 최고 점수를 개선하는 이동은 열망 기준으로 허용합니다.
5. 정체되면 재시작하거나 일부 순서를 섞고, 정한 예산 안에서 탐색한 뒤 최고해를 반환합니다.

처음에는 선발·수비 배정과 타순을 나누어 탐색해도 됩니다. 다만 선발이 바뀌면 좋은 타순도
달라지므로, 확장할 때는 두 단계를 번갈아 개선하고 최종 명단 전체를 같은 목적함수로 평가합니다.

중복 선수, 다른 팀 선수, 투수 자리 위반, 공수 명단 불일치는 이웃 생성이나 복구 단계에서
방지하고 최종 검사도 수행하세요. **포지션이 다른 타자를 수비에 배치하는 것은 유효한 해**이므로
무조건 제외하지 않고 실책 비용으로 반영할 수 있습니다. 현재 엔진에서 해당 수비수에게 실제로
수비 기회가 주어지는지도 고려합니다(포수 관련 제한은 7절 참고).

### 10.4 목적함수 개선과 탐색 개선을 구분해 비교합니다

수업에서는 다음 두 단계로 실험하면 어떤 부분이 좋아졌는지 확인하기 쉽습니다.

| 단계 | 고정할 조건 | 비교할 결과 |
|---|---|---|
| 공통 목적함수로 TS·GA 구현 | 같은 입력·목적함수·평가 횟수 예산. 캐시 적중을 횟수에 포함할지도 통일 | 최고 fitness, 평가 횟수에 따른 수렴, 실행시간 |
| 목적함수까지 자유롭게 개선 | 같은 시간 제한·경기 조건·비교 상대 | 실제 경기 승점률, 평균 득실차, 폴백 횟수 |

학생마다 목적함수가 다르면 **fitness 숫자 자체를 서로 비교할 수 없습니다.** 자유 설계 단계에서는
여러 팀과 시드로 실제 경기를 반복하고, 가중치 튜닝에 쓴 조건과 최종 평가 조건을 나눕니다.
공통 목적함수에 타순 연결 효과까지 넣어 시작한 뒤, 맞대결·체력·경기 상황을 하나씩 추가하며
개선 여부를 확인하는 방식을 권장합니다. 경기 반복 실행 방법은 3절을 참고하세요.

## 11. 제출 전 검사와 경기 중 실패 처리

파일을 올리면 두 단계로 검사합니다.

| 단계 | 확인 내용 |
|---|---|
| 정적 검사 | Python 문법, 함수 위치·인자, 반환문, 금지 호출과 주의할 코드 |
| 실행 검사 | 선택 구단으로 `decide_lineup`을 한 번 호출, 시간 제한과 `{defense, offense}` 명단 규칙 확인 |

| 표시 | 예시 | 대응 |
|---|---|---|
| 오류 | 문법·시그니처 오류, `input()`, 종료 호출, 외부 명령 실행, 실행 실패·무효 명단 | 수정 후 다시 업로드 |
| 경고 | 전역 난수, `time.sleep()`, `while True`, 파일 접근·일부 모듈 import | 내용 확인 후 규칙에 맞게 수정. 경고만으로 시작이 차단되지는 않음 |
| 참고 | 디버깅 출력, `global`, 최상위 실행문 | 불필요한 출력·초기화 비용 점검 |

검사 통과는 **해당 구단·첫 이닝 조건에서 한 번 실행해 봤다는 뜻**입니다.
모든 구단, 지친 선수, 다른 타순 시작 위치에서도 성공한다는 보장은 아닙니다.
특히 `None`인 이전 명단과, 맞대결 행이 없는 투수–타자 쌍도 처리하세요.
사전 검사와 실제 경기의 `matchups` 크기가 같다는 보장도 없으므로, 표가 커져도 제한시간에
여유가 있는지 확인하세요.

실제 경기에서 시간 초과·예외·무효 반환(dict 형식·규칙 위반)이 발생하면 다음과 같이 대체합니다.

- 직전 이닝에 제출한 유효한 명단(`defense`+`offense`)이 있으면 그대로 재사용합니다.
- 없으면(예: 1이닝) 기본 수비 10명과 그 앞 9명의 타순으로 출전 처리합니다.

실패 시에도 이번 이닝 선발 선수는 바뀌지 않습니다.
자동 패배나 경기 전체 중단이 아니라, 명단을 대체하고 경기를 계속하는 방식입니다.

매 호출은 새 프로세스에서 실행됩니다. 전역 변수에 저장한 값이나 DataFrame 수정은 다음 호출로 이어지지 않습니다.
모듈 import와 최상위 실행문도 매번 실행되므로 가볍게 유지하세요.
기본 10초는 함수 본문만 따로 측정하는 제한이 아닙니다. 자식 프로세스 시작·import 등 부가 비용을 고려해 여유를 두세요.

입력 대기, 프로세스 종료, 외부 명령, 파일·네트워크 조작을 제출 코드에 넣지 마세요.
정적 검사는 일부 패턴을 확인하며, 실행 환경이 모든 금지 동작을 기술적으로 차단하는 것은 아닙니다.
일반 계산용 표준 라이브러리와 설치된 `pandas`·`numpy`를 사용하고, 추가 패키지에 의존하지 않도록 작성하세요.

## 12. 제출 전 확인

- [ ] 최상위 함수의 이름·인자 이름·순서를 지켰다.
- [ ] 공격은 수비 앞 9명과 같은 선수이고, 수비 10명 중 마지막은 투수다. 정수 pCode이며 중복이 없다.
- [ ] 구단이 바뀌어도 `my_team`에서 명단을 만든다.
- [ ] 타순 시작 인덱스, 이전 명단 `None`, 맞대결 행이 없는 투수–타자 쌍(및 빈 표)을 처리한다.
- [ ] 난수는 전달받은 `rng`만 사용한다.
- [ ] 체력 0과 기록 0을 결측값으로 바꾸지 않는다.
- [ ] 실제 채점 환경에서 시간 제한에 여유가 있고, 파일을 다시 올려 검사했다.
