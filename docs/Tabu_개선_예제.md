# 개선형 Tabu Search 예제

제출 파일은 [example_tabu_advanced.py](../examples/example_tabu_advanced.py)입니다.
필요한 함수가 한 파일에 있고, `math`와 `pandas`만 import합니다.
엔진 내부 모듈이나 고정 선수 목록에 의존하지 않으며, 난수는 전달받은 `rng`만 사용합니다.

## 선발과 타순을 나눠 탐색합니다

현재 규칙은 **이닝 시작에 투수 포함 10명을 선발하고, 공수교대 때 같은 선수들을 유지**하는 방식입니다.
수비 호출에서는 전체 후보 중 10명을 고릅니다. 이어지는 공격 호출에서는 `my_team`에 선발 10명만
들어오므로, 투수 제외 9명의 타순만 바꿉니다. 선발 DH도 반드시 타격합니다.

| 항목 | 기존 Tabu 예제 | 개선형 |
|---|---|---|
| 출전 선수 | 기록·체력으로 수비 배정 탐색 | 선발 9명의 타격 기여, 실책 비용, 수비 체력 손실을 함께 평가 |
| 공격 평가 | OPS·OBP·SLG와 현재 체력 | 사건별 기록의 표본 보정, 상대 투수·맞대결, 예상 체력 반영 |
| 타순 | 고정 타순 가중치와 시작 위치 보정 | 실제 선두부터 평가한 뒤 엔진의 시작 인덱스에 맞춰 반환 |
| 투수 | ERA·기초 스태미너·현재 체력 | 누적 투구 수와 목표치로 추가 4·12·22구 시점의 실점 위험을 근사 |
| 타부 | 이동한 배정 일부를 금지 | 빠진 선수가 원래 슬롯으로 복귀하는 역이동을 금지. 교환은 두 슬롯 모두 기록 |

수비에 나서는 타자는 스윙 환산 3~5회의 체력을 소모하므로, 타격 능력과 수비 비용을 함께 봅니다.
DH에는 수비 소모가 없습니다. 포지션이 다른 타자를 수비에 배치할 수 있지만,
해당 선수가 관여하는 수비의 실책 확률에 불이익이 있습니다.

## 탐색 구조

해는 타자 9명의 슬롯 배정이며, 선발과 타순 모두 같은 `_tabu()` 탐색기를 사용합니다.
선발 단계에서는 두 슬롯 교환과 벤치 선수 교체를 탐색합니다. 타순 단계에는 후보가 선발 9명뿐이므로
슬롯 교환만 가능합니다. 투수는 별도로 모든 후보를 비교해 10번째 자리에 추가합니다.

현재 해보다 나쁜 이동도 허용하되, 지금까지 가장 좋은 해를 보존합니다.
최근 이동의 역이동을 금지하고, 전체 최고 점수를 개선하면 타부를 해제하는 열망 기준을 적용합니다.
개선이 정체되면 최고해를 섞어 다른 배치에서 다시 탐색합니다.

반복은 80회, 반복당 이웃은 40개입니다. 벽시계 시간에 따라 중단하지 않으므로 같은 입력과 `rng`에서
결과가 재현됩니다. 실제 제한시간에는 프로세스·import 비용도 포함되므로 제출 환경에서 검사하세요.

평가식은 기대 득점의 근사입니다. `PRIOR`, `RUN_WEIGHTS`, 수비 기회비중과 체력 손실 가중치는
예제에서 정한 가정이며, 정확한 엔진 확률이나 숨겨진 개인 실책 성향을 읽어오는 값이 아닙니다.

## 실행과 비교

프로젝트 최상위에서 환경을 활성화한 뒤 실행합니다.

```shell
python -m kbo_sim.server --a-name 개선Tabu --a-team 삼성 --a-algo examples/example_tabu_advanced.py --b-name 기존Tabu --b-team KT --b-algo examples/example_tabu_lineup.py --seed 42
```

비교 도구는 삼성/KT, LG/KIA, 두산/NC, 롯데/SSG, 한화/키움 다섯 조합에서
같은 시드마다 알고리즘의 팀·홈/원정 배정을 뒤바꿔 두 경기를 실행합니다.

```shell
python tools/compare_tabu.py --check --seeds 2 --seed-start 910000 --out output/tabu_comparison.json
```

`--check`는 10개 구단의 실제 업로드 검사(10명 선발 → 선발 9명 타순)를 수행하며,
지친 상태·빈 맞대결 표·같은 rng의 재현성도 확인합니다.
기본 비교 모드는 **저장소의 두 예제만 같은 프로세스에서 실행**합니다.
실제 경기 엔진과 명단 검증을 사용하지만 하드 타임아웃과 프로세스 격리는 적용하지 않으므로,
빠른 모드의 호출시간을 실제 채점 시간으로 해석하지 마세요.

일반 서버와 같은 격리 방식으로 비교하려면:

```shell
python tools/compare_tabu.py --isolated --seeds 1 --pairs 1 --seed-start 910000 --out output/tabu_comparison_isolated.json
```

`--seeds`는 구단 조합별 시드 수이고 `--pairs`는 앞에서부터 사용할 구단 조합 수입니다.
총 경기 수는 `seeds × pairs × 2`입니다. JSON에 규칙 식별자 `lineup_policy: "locked_roster_10"`,
경기별 조건·점수·승자, 호출시간과 폴백 횟수를 저장합니다.

## 현재 규칙에서의 확인 결과

선발 10명 고정 규칙으로 20경기를 다시 비교했습니다. 각 시드에서 팀·홈/원정을 교환했습니다.

| 비교 | 개선형 승/무/패 | 승점 비율 | 득실점 차 |
|---|---|---|---|
| 20경기, 시작 시드 910000 | 8승 2무 10패 | 45.0% | +10 |

승점 비율은 `(승 + 0.5 × 무) / 경기 수`입니다. 양쪽 모두 폴백은 0회였으며,
개선형은 10개 구단의 실제 제출 검사와 지친 상태·빈 맞대결 표·재현성 검사를 통과했습니다.
결과 원본은 [현재 규칙 20경기와 제출 검사](../output/tabu_locked_roster.json)입니다.
첫 시드 2경기를 [실제 격리 방식](../output/tabu_locked_isolated.json)으로도 실행해 점수·승자가 일치함을
확인했습니다. 폴백은 0회이고 개선형의 최대 호출시간은 약 1.41초였습니다. 이 2경기는 중복 검증이므로 20경기에 더하지 않습니다.

이 표본에서는 승점 기준으로 기존 예제를 앞서지 못했습니다. 이름의 ‘개선형’은 추가한 탐색·평가 기법을
구분하기 위한 것으로, 현재 규칙에서 더 높은 승률을 보장하지 않습니다. 평가 가중치를 바꿀 때는
조정에 사용하지 않은 시드에서도 비교하세요.
